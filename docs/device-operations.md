# 设备详情、文件管理与批量巡检

设备列表的“详情 / 文件”打开详情抽屉，展示注册描述、最后注册时间、连接来源、协议号和最近操作。协议号不是软件版本，离线原因也不会凭空推断。

新登记的设备自动建立运维配置：执行账号 `nvidia`、目录范围 `/`，手动登记和显式开启的兼容自动登记均适用，无需再手动保存设置。已有设备的配置保留，不批量覆盖。目录范围为 `/` 不会提升为 root 权限；没有 `nvidia` 账号的设备应由平台管理员改为实际存在的非 root 账号。

平台管理员仍可进入设备详情的“运维设置”，自定义非 root 系统账号和允许访问的绝对目录。设备需已有支持命令协议的 rtty 客户端与 Python 3；不安装 FTP/SFTP 服务。173 已配置账号 `nvidia`、目录 `/`（按用户后续要求开放浏览，仍受 nvidia 的系统权限约束）。

文件目录浏览仍使用受限命令通道。文件内容改走独立 WebSocket 会话，复用原有 rtty MsgTypeFile 二进制通道、下载窗口16与上传窗口4（32 KiB块），不再逐块启动 Python 或进行 Base64 编码。每个文件只启动一次非 root Python 包装程序，负责目录、系统账号、大小和 SHA-256 校验，并调用原有 rtty 文件助手。原有终端文件传输继续可用。

- 文件操作要求当前账号拥有该设备的操作权限；查看者不能操作文件。
- 目录不能越界；越界符号链接也会被拒绝。只允许访问配置账号本身有权限的文件。
- 单文件上限 16 MiB，单目录最多列出 300 项。不覆盖同名文件。
- 二进制上传使用目标目录下的临时目录、SHA-256 校验、原子且不覆盖的提交；取消会终止专用会话并清理临时目录。失败后可重新上传，不支持中途断点续传。
- 设备离线或浏览器退出时，清理可能未完成，残留位于允许目录下的 `.rttys-transfers`；范围为 `/` 时位于 `/tmp/.rttys-transfers-UID`。恢复后可重试取消；达到 20 个未完成传输时拒绝继续创建。未实现断点续传和自动清理策略。
- 二进制下载保持打开的文件描述符，检查大小、修改时间与 SHA-256；服务端和浏览器都核对收到的完整内容。

“批量任务”仅向当前租户管理员开放。按设备选择，分组用于筛选；一次最多 20 台设备，后端去重并逐台重新检查权限。

当前模板：磁盘检查、失败服务状态、当前系统账号可读日志。没有任意脚本或服务重启能力。每台设备保存输出、退出码和失败原因；离线、权限撤销和非零退出码不会标记成功。服务器重启将未完成任务标为中断，不自动重试。

任务和文件操作复用受审计访问租约。权限撤销可阻止继续请求或读取响应，但已经发送到设备的操作不承诺立即终止；客户端命令执行有 30 秒超时。

本次增加独立 `device_operations`、`operation_tasks` 表，不修改原身份表 schema v3。旧版本忽略这些表，回退时保留当前数据库，不用旧备份覆盖新增用户数据。

## 验证

在隔离 Linux 测试环境以 root 运行：

```sh
python3 scripts/operations-live-e2e.py \
  --server /absolute/rttys \
  --client /absolute/rtty \
  --os-user EXISTING_NON_ROOT_USER
```

脚本在临时目录启动真实服务端与客户端，不操作 systemd；验证 TLS 注册、目录读写、中文及特殊字符文件名、分块重试、SHA-256、覆盖拒绝、越界及符号链接拒绝、取消清理、批量去重和离线失败。日志模板通过隔离的假 journalctl 返回 7，专门验证非零退出码会标记失败并保留输出，不能把此测试描述为真实系统日志采集验收。

脚本输出证据目录，失败和成功都写 checks.json。既有 `scripts/run-local-e2e.py` 还覆盖跨租户详情拒绝、查看者文件与批量任务拒绝、租户管理员不能修改设备 OS 账号。

## 二进制传输验收（2026-10-27）

客户端必须安装 rtty-tenant-poc 文件助手，并配置 username 使专用终端直接进入与运维设置一致的非 root 用户。默认系统登录需要交互密码或账号不匹配时，文件传输明确失败，不会自动提权。

入口 GET /api/devices/:id/file-transfer 只接受文件数据和文件控制消息；禁止浏览器发送终端输入。目录边界、租户隔离、权限租约、取消及每次传输审计继续生效。每个文件最多16MiB，会话超时5分钟。旧HTTP分块API仅保留兼容，更新页面不再用它传输文件内容。

命令重放：go build -o /tmp/file-manager-check ./cmd/file-manager-check；使用 -access 私有fixture -ca 服务器CA -source 设备已存在测试文件 -directory 专用测试目录 -output 验证JSON。-download-only 可只测速，-read-delay 100ms 可模拟慢接收端。测试会在专用目录创建随机上传文件；不操作业务文件。

公网173同一个1MiB文件：旧HTTP串行链路11.7607秒，二进制链路0.9779秒，约12.03倍；1MiB上传0.9065秒，回读1.0052秒；8MiB下载2.9937秒（2.67MiB/s）。时间包括连接准备和完整性确认，属于本次网络环境样本，不代表带宽上限。

1MiB下载、上传回读、8MiB下载SHA-256均一致；错误校验值、取消、同名覆盖、终端注入均拒绝；173目标目录无残留临时上传目录。Chrome网页实际下载8MiB后，本机文件摘要与设备源文件一致。网页上传自动选文件因Chrome扩展缺少文件URL权限未完成；真实HTTPS/WebSocket协议上传已在173完成。

修复过程中保留的失败证据：终端登录未就绪导致命令丢失；公网完成时过早关闭TCP导致尾部重置；服务重启后173尚未重连的409。现已分别通过就绪探测、接收端完成关闭握手、等待设备上线处理。慢速接收端测试通过。

## 设备编辑与租户功能授权

设备列表的“编辑”可一次修改显示名称和多个分组；更新同一事务提交，未知分组或无效名称不产生部分更新。平台登记编号、Token、设备内部ID与OTA绑定不变。分组变化仍按有效授权并集重验会话，改名本身不会断开有效连接。接口为 PUT /api/manage/devices/:id/details {name,groups}，仅当前租户管理员可操作，跨租户隐藏为404。

平台admin在“租户与账号 → 功能授权”管理应用升级OTA、批量任务、文件管理、Web代理；远程终端是基础能力。未配置开关的既有或新增租户保持原有功能可用，仍需原角色及设备授权。设置接口 PUT /api/manage/tenants/:id/features {features:{ota,tasks,files,web}} 要求四项完整布尔值，仅平台admin可保存，权限与审计一并持久化。

关闭文件或Web授权会撤销对应受管通道，终端保留；终端原生文件传输控制也会被拒绝。拥有终端的账号仍能按操作系统权限使用shell读写文件，功能授权不是文件系统隔离。已受理的OTA部署不自动撤回，正在设备上执行的命令也无法承诺终止；后续请求与尚未执行的批量操作重新检查功能权限。

OTA授权不替代后端接入。租户列表和授权抽屉展示ota_backend_ready；已授权但后端未就绪时，升级页明确提示未配置。Mender地址、租户制品隔离及设备绑定仍需由部署管理员完成，不会因勾选而自动执行升级。

迁移增加独立tenant_features表，不改身份schema v3。首次部署按结构变更做快照；普通后续更新仍复用原数据库。恢复旧程序前应核对其是否支持已关闭的功能授权，旧代码不会识别新功能开关，不应将回退解释为保留这套权限语义。
